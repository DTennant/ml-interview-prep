ML Coding

  • Google Colab，basic Python 环境

  • 边写边讲：先说 shape 和思路，写完一段就跑一下

  • 按你的背景和你可能要做的工作出题
  • 共享屏幕，用 Excalidraw 画图
  • 中途可能在 Colab 里写一小段代码

2.4 Debug 题

给一段训练代码，问 loss 为什么不降或者变成 NaN。常见埋的 bug：

  • 忘了 zero_grad()
  • F.cross_entropy 前面又做了一次 softmax
  • mask 方向反了
  • softmax / argmax 用错了维度
  • logits 和 labels flatten 的顺序不一致
  • 广播错误（(N,) 和 (N,1) 相减）
  • learning rate 太大 / 没有 warmup
  • 数据没有 shuffle
  • eval 时没调 model.eval() / 没加 no_grad
  • label 是 float 而不是 long
  • log(0) 导致 NaN
  • logging 时没 .item() 或 .detach()，导致内存泄漏

练习：06 里有一个埋了 6 个 bug 的版本，先自己找，再看修好的版本。

2.7 现场节奏

  1. 复述题目，确认输入输出的 shape 和边界条件（1 分钟）
  2. 口头讲思路，标出每个张量的 shape（2 分钟）
  3. 先写最简单、能跑通的版本，跑一下
  4. 加测试：拿 PyTorch 自带实现做参照，或者 gradient check，或者 sanity check（概率之和为 1、mask 掉的位置为 0）
  5. 再优化：数值稳定、向量化，讲清楚复杂度和显存
最常丢分的地方：shape 和广播出错、写不出数值稳定的版本、写完不验证。

3. System Design

3.1 时间分配（按 45–60 分钟算）

  1. 澄清需求，5 分钟：目标是什么、规模多大（同时跑多少任务、算力预算多少）、怎么衡量成功、哪些地方允许出错
  2. 整体架构，10 分钟：先把各组件和数据流画出来，不要一开始就钻细节
  3. 深入 2–3 个组件，20 分钟：主动选你最强的部分，同时看面试官想往哪个方向追问
  4. 规模、失败和取舍，10 分钟：瓶颈在哪、挂了怎么恢复、成本怎么控制
  5. 怎么证明系统真的有效，5 分钟：research 公司特别看重这一块

3.2 题库

A. 自我改进 / 自动化 ML research 的 agent 系统（最可能）

给一个任务和评估指标，系统自己提方案、跑实验、迭代。

  • 生成候选：LLM 提方案，加上历史尝试记录（memory），避免重复试一样的想法；历史记录怎么压缩后喂给 LLM
  • 搜索策略：tree search、进化、bandit（UCB / Thompson sampling）、successive halving。讲清楚怎么平衡探索和利用，以及预算怎么分配
  • 执行：每个候选在沙箱里跑，用容器隔离，设好超时、CPU/GPU/内存限制和网络隔离
  • 评估：分开 held-out 和 validation 数据，用多个 seed 处理噪声，结果要做显著性检验（paired bootstrap）
  • 风险：过拟合 eval、reward hacking（改 eval 代码、读 test label、硬编码答案）、eval 泄漏。对策：eval 放在 agent 碰不到的环境里，把 validation 和 test 分开，加 sanity check，定期人工抽查
  • 工程：结果缓存（按代码 + 配置 + seed 做 hash）、重复候选去重、失败重试，每个改进怎么来的、跑出什么结果都要能追溯和复现
  • 指标：单位成本带来的提升、多久找到最优解、改进能不能迁移到 held-out 任务
B. 大规模 agent eval / rollout 平台
  • 任务队列 + 调度（K8s / Ray），GPU 推理和 CPU 沙箱分开调度和扩缩容
  • LLM 调用走一个单独的推理服务（vLLM / SGLang），做 batching 和限流；用外部 API 时要处理 rate limit、重试和成本上限
  • 沙箱：镜像预构建 + 缓存，冷启动要快；多步工具调用时环境状态怎么管理；超时处理
  • 结果的确定性：固定 seed / temperature，记录模型版本和镜像 hash
  • 存储：结构化结果放数据库，完整 trajectory 放对象存储；能按任务、模型、版本查询和对比
  • 可观测性：dashboard、失败原因自动分类（环境错误 / 超时 / 模型错误）、成本监控
  • 规模估算示例：1 万个 rollout × 每个 10 分钟 ÷ 2 小时完成 → 大约 830 个并发沙箱
C. Agent RL 训练 pipeline
  • actor（vLLM 生成 rollout）和 learner（FSDP / Megatron 训练）分开部署；同步训练 vs 异步训练
  • 异步训练时数据 staleness 怎么处理：限制 policy 版本差、用 importance ratio 修正或 clip、丢掉太旧的数据
  • 权重同步到 actor：NCCL broadcast / 写到共享存储，多久同步一次
  • 奖励：verifier / 单测 / reward model；长任务奖励稀疏，credit assignment 怎么做；防 reward hacking
  • 多轮工具调用：环境放在单独的服务里；tool 返回的 token 要 mask 掉，不算进 loss
  • 长尾问题：有些 rollout 特别长，会拖慢整批 → 部分 rollout 先训、超时截断、动态 batch
  • 监控：reward 曲线、KL、entropy、response 长度、各种 clip 被触发的比例
D. LLM 推理服务
  • continuous batching；prefill 和 decode 两个阶段的特点不同（prefill 受算力限制，decode 受显存带宽限制）
  • KV cache 显存管理：PagedAttention、prefix caching（相同的 system prompt / few-shot 前缀可以复用）
  • throughput 和 latency 的取舍：batch size、TTFT（首 token 延迟）、TPOT（每个 token 的生成时间）
  • 多模型路由、量化、speculative decoding、tensor parallel
E. 其他可能的题
  • 训练数据 pipeline：爬取 → 去重（MinHash）→ 质量过滤 → 配比；怎么防止 eval 数据污染训练数据（n-gram overlap 检测）
  • 大规模分布式训练：DP / TP / PP / FSDP 分别切什么；怎么存 checkpoint，节点挂了怎么恢复
  • 实验追踪和复现系统：怎么管理配置、代码版本（git commit）、随机种子、数据版本和产出文件
  • reward model / verifier 服务，以及怎么防 reward hacking

3.3 几乎每道题都会追问的点

  • 规模估算：多少张 GPU、跑多久、花多少钱、能撑多少并发
  • 出错了怎么办：任务挂掉、节点挂掉、结果不确定（同样输入跑出不同结果）、重试要幂等
  • 评估可信度：噪声怎么处理、要不要多个 seed、held-out 集、显著性检验
  • 安全和隔离：沙箱逃逸、网络访问、资源耗尽
  • 取舍：为什么选同步而不是异步，代价是什么，怎么缓解
  • 演进：先做 MVP，规模扩大 10 倍时哪里先成为瓶颈

3.4 中途可能要写的代码

一般是小组件，提前写一遍就不会卡（→ 09）：async worker pool 加超时、重试和指数退避；UCB bandit；paired bootstrap 显著性检验；结果缓存和去重；successive halving。

4. 要背熟的数字

项目数
参数显存（bf16）2 bytes × 参数量：7B 约 14GB，70B 约 140GB
训练显存（mixed precision + Adam）约 16 bytes / 参数（bf16 权重 2、梯度 2、fp32 master 权重 4、Adam m 和 v 共 8），还没算 activation
KV cache 大小2 (K,V) × 层数 × KV 头数 × head_dim × 2 bytes，算出来是每个 token 的大小；Llama-2-7B（32 层，32 头 × 128）约 0.5MB/token，4k 上下文约 2GB；用 GQA 可以按比例缩小
训练 FLOPs≈ 6 × 参数量 × token 数（forward 2N + backward 4N）
推理 FLOPs≈ 2 × 参数量 / token
H100约 1000 TFLOPS（bf16 dense）、80GB HBM、带宽约 3.35 TB/s；实际 MFU 一般在 40–50%
decode 吞吐上限（batch 为 1）约等于显存带宽 ÷ 权重大小：7B bf16 在 H100 上约 3.35TB/s ÷ 14GB ≈ 240 tokens/s
Attention 复杂度时间 O(T²·d)，score 矩阵占显存 O(T²)（FlashAttention 不把整个矩阵放进显存）
